# Pulse 的理念与设计思想

> 这篇讲**为什么**这样设计：几条贯穿全仓的公理、各自的代价与边界，以及由此「刻意不做什么」。
> 具体形状（类型、签名、时序、冻结面）见 [`pulse.md`](pulse.md)；**对象模型已按
> [#311](https://github.com/Luo-root/pulse/issues/311) 定案并实现**，契约与旧模型的迁移缘由见
> [`object-model.md`](object-model.md)。

## 定位

Pulse 的产品方向是**数据驱动、可观测、可组合的 Go workflow-engine 基座**。当前 `pulse` 提供可嵌入的单进程执行内核、图观测与完整节点链的检查点桥接；独立的 `pulse-durable` 已有 Store/Codec、Run/Resume、方案 A 子图恢复与本机文件后端。持久化等待与分布式运行管理是后续设计方向。两仓职责、现状与开发顺序见 [workflow-foundation.md](workflow-foundation.md)。

下面的公理约束**执行内核**。核心只做三件事：

1. **声明**：谁读什么、谁写什么（`Requires` / `Provides`）；
2. **推进**：一条 Key 到达（有值或显式跳过）就让等它的节点具备就绪条件——没有边对象、没有「先排序再执行」的调度阶段、没有调度循环；
3. **讲清楚**：跑到哪了、谁在等谁、失败在哪（`Observer` 事件 + 结构与状态视图）。

它不是这些：不是**传统的中心调度式 DAG 工作流引擎**——Pulse 同样从 `Requires` / `Provides` 推出依赖图、同样拒绝依赖环、同样给拓扑视图（`Topology()`），差别在于**推进**不由中心调度器决定，而是由 Key 到达驱动；重试必须**显式声明**（`Retry` 切面）——声明之后，那一段的槽位写入由引擎按**尝试边界**管住（失败的那一次不发布给下游），但引擎**绝不**替你隐式补偿、也不会去撤你已经在外部世界里做过的事；不是业务框架（不碰 IO、不认识业务字段）；不是 DSL（Go 里就是 Go，声明式只在 `pulse/yaml` 那一层存在）。

## 八条公理

### A1 拓扑由数据推出来，不由人写

**一句话**：节点只声明 `Requires` / `Provides`；边是「谁生产这条 Key、谁消费它」推出来的。

**为什么**：写边就会写错边——漏一条、指错一端。而「这条 Key 谁生产」在声明里本来就唯一：一个 Key 至多一个来源（否则 `ErrDuplicateSource`，见 [`graph.go`](../../graph.go)）。既然唯一，边就是**派生视图**，不该是输入。`Topology().Edges` 因此是算出来的，不是存下来的。

**代价**：不支持「同一对节点多条边、分别表达」这类图论玩法，也不支持同名 Key 多来源。要那种表达力，Edge 就得变成一等资产——那正是本仓刻意不要的复杂度。

### A2 声明与到达分开（`pending` 不是到达）

**一句话**：槽位只有三态 `pending` / `ready` / `skipped`；`pending` 是「还没到」，不是「到了但没值」。

**为什么**：把两者混起来，下游就会在「输入还没来」时以为自己该跳过了；而「谁在等谁」也就答不出来（看板会把「还没轮到」与「等名额」画成同一个样子）。

**住哪**：`slot`（[`slot.go`](../../slot.go)）；`Get` 阻塞到到达、`TryGet` 非阻塞看一眼、`WaitAll` 报「谁没到」。零值与「没有」是**两件事**：要区分就写 `skipped`（显式的第三个状态），别拿零值当缺失。

### A3 缺失 / 跳过是正常语义，不升格为失败

**一句话**：跳过是**到达**（这一轮这件事就是「没有」）——正常终结、不阻塞、不报错；反过来，失败也**不得**降格成跳过。

**为什么**：数据流里「这路没有」是常态（可选输入、分支没走到、上游按条件省略）。把它当异常，等于逼每个节点写兜底样板；而把失败伪装成跳过，会让「要谁来修」这件事从故障单里消失。

**住哪**：门闩的判据是「有没有值」而不是「有没有跳过」——一条值都没到才轮到节点自己跳过；`*SkipError`（[`errors.go`](../../errors.go)）是**显式的 fan-in 策略声明**，`WaitAll` 的返回值直接 return 就是「缺一条就别跑我」。

**代价**：汇聚默认「到几个收几个」。想要「缺一不可」，必须自己写出来——引擎不替调用方猜。

### A4 错误显式，且在最早能判定处报

**一句话**：能静态判定的错绝不留给运行期；报错要点出「哪一处、为什么、怎么改」，而不是一句「失败」。

**为什么**：图跑起来之后的毛病最贵——挂死、超时、静默拿到零值，三种都难查，而且都不指向真正写错的那一行。

**住哪**：`Start` 一次判掉静态毛病并报**第一条**（没来源的 `Requires`、声明了却没人产出的出口、依赖环——环给出一条具体见证路径、流式出口的接线，判据在 `problems.go`，`Validate` 让人在装配期反复问，**通过即封口**：封的是**整棵子树**，挂着的子图也一起冻）；声明式装图（`pulse/yaml`）在 `Load` 那一刻按**引用点**校验子图（同一份 spec 被两处引用时两处的 `in:` 可以不同，按并集校验等于放过一张会炸的图），报文点明**挂载路径**——谁也引用不到的 spec 例外：它没有挂载点就没有接口面，「这条键没人喂」在那里判不了，只查真判得了的那几条；报错文案点名位置（`Sub "b"`、`node "x"` 那类）。

**阶段 1 补上的那一半**（#311）：`pulse.Sub` 的**绑定**校验已经从运行期搬进装配期，而且**判据只有一份**——端口只能接声明过的入口 / 出口，类型不符、接到内部中间 Key、组合环、子图里的无来源与依赖环，都在装配期（yaml 则是在 `Load`）报完，报错点明挂载位置。

**代价**：装配期多一遍校验；某些「严格」会让本来也许能跑起来的图报错——我们选择报错，因为它迟早会炸，而炸在装配期比炸在半夜便宜。

### A5 观测与语义同源，且观测不改语义

**一句话**：事件与状态**在同一点写**（先写状态、再发回调）；观察者抛 panic 不会变成节点失败；业务维度只能走 `Attrs`，不往 `Record` 上加具名字段。

**为什么**：两套口径就会漂——看板说 A、日志说 B，谁都对。而观测一旦能改语义，它就不再是观测，是隐式控制流。

**住哪**：`runNode` 的几发回调（[`execution_run.go`](../../execution_run.go)）；`Record` + `Attrs` 与 `<component>.<field>` 键约定（[`observe/`](../../observe/)）；`MultiObserver` 的扇出隔离。

**代价**：想加一个「引擎认识的业务字段」无处可写——只能进 `Attrs`，且键名归定义它的包所有。

### A6 引擎零依赖，能力分层

**一句话**：`pulse` 只用标准库；观测在 `observe`、声明式装图在 `yaml`；依赖方向单向（`pulse` ← `observe` / `yaml`）。

**为什么**：引擎是别人系统里的地基，不能把依赖树带进宿主的供应链；而观测 / 装配是可以选装的能力。

**住哪**：`go.mod` 里唯一的第三方依赖 `gopkg.in/yaml.v3` 只被 `yaml` 包使用；`go list -deps .` 只有标准库。

**代价**：不引重试 / 指标 / 配置生态的轮子，相关的都自己写小份；别人给出的生态件要接就写在宿主侧或独立包。

### A7 代价写进文档：冻结面与诚实边界

**一句话**：会破坏调用方的语义（槽位三态、哨兵判据、回调次数、编码原语）写进**冻结面**；做不到的事写进**刻意不提供**，破坏性变化在 release notes 里点名。

**为什么**：库的价值有一半在可预测——使用者要知道什么**不会**变。

**住哪**：`pulse.md` 的「附 · 冻结面与不提供的东西」、`AGENTS.md` 的 Freeze contract、CI 里的文档示例闸门（`TestDocsExamplesUseCurrentSignatures`）。

**代价**：想改旧形状要付迁移成本（minor 版本 + 迁移说明），不能偷偷改。

### A8 声明可复用，运行独立（阶段 1 / 2 / 3 已落地）

**一句话**：**图是定义，执行是实例**——同一张图应当能被顺序、并发地执行多次，每次有独立的槽位 / 状态 / 错误 / 取消域。

**为什么当初先用一次性模型**：那时 `Graph` 同时是定义与一次执行（`Start` 只能一次、`Wait` 释放并取消图的 ctx、槽位与节点状态都挂在图上），`Sub` 还要在运行期用 `build` 造子图——于是「组合完成但尚未运行时看不到完整结构」「构建 / 绑定错误延迟到运行期」这些限制互相牵连。先用一次性模型把数据流语义（三态、跳过、门闩、观测）跑通并冻住，再拆对象；反过来会把「语义对不对」和「对象边界对不对」搅在一起，谁也定不下来。

**落地进度**（按 [#311](https://github.com/Luo-root/pulse/issues/311) 分阶段，细则见 [`object-model.md`](object-model.md)）：阶段 1 静态组合（`Sub` 挂现成子图 + 端口 + 整棵子树封口）、阶段 2 `Execution` 拆分（定义不含任何运行态、每处挂载一份子执行）、阶段 3 事务性 `Retry`（attempt 写集：失败那一次的写不发布给下游）**都已落地**；阶段 4（快照 / 观测 / YAML 对齐）已实现（#319，静态接口、执行快照、Mermaid 与 YAML Analyze 均已具备）：静态结构看 Topology，运行进度看 Execution 的无值快照；Mermaid 从结构派生，YAML Analyze 不依赖注册表。阶段 5 负责迁移与发布收口。

**代价**：迁移期公开面会动（0.x 允许 minor 破坏），文档必须说清哪份描述**现状**、哪份描述**目标**，每批改动同步示例与迁移说明。阶段完成不自动发版：Pulse v0.5.0 已正式发布（e60254c）；Durable v0.1.0 及 sqlite/postgres 子模块 v0.1.0 已发布（532bced），受维护数据库 Store [#40](https://github.com/Luo-root/pulse-durable/issues/40) 已交付。两仓不共用发布闸门；当前 Pulse 准备 Go 1.26 / v0.5.1，尚未发布，仍需完成本版审查、回归与跨仓组合验证。发版由维护者决定；之后继续 0.x 小步迭代，达到项目目标且不再有可预见的系统性重大变更后，完善详细文档并发布 v1.0.0，基本固定 API 与实现。具体闸门见 [`workflow-foundation.md`](workflow-foundation.md) §8。

## 因此刻意不做

这里的边界针对执行内核。`pulse-durable` 已有的检查点存储与恢复，以及后续的持久化等待、任务领取与接管，属于另一层运行管理；这些能力不受“核心没有中心调度循环”这一实现选择禁止，具体范围以开发总纲和对应实施票为准。

| 不做 | 因为 |
|---|---|
| 中心调度器与「先拓扑排序再执行」 | 数据到达就推进；执行顺序是声明的**结果**，不是前提（A1）；拓扑视图是只读出口，不参与推进 |
| 「缺值即跳过」的隐式策略 | 缺失语义必须由节点显式声明：门闩默认「到几个收几个」，`WaitAll` 才是「缺一不可」（A3） |
| 回滚用户的外部副作用 | 引擎只管自己手里的槽位。数据库提交 / HTTP / 写文件那一层要事务、幂等键或补偿，且必须由调用方接进来（[`object-model.md`](object-model.md) 的事务边界） |
| 隐式补偿与不透明的事务魔法 | 没有单独契约与测试之前不引入——听起来像保证、实际是运气（A4） |
| 把业务维度塞进引擎类型 | `Record` 不加具名字段，`Attrs` 是唯一出口（A5） |
| 在 Go 里造 DSL | Go 里就是 Go；声明式只在 YAML 那一层，且与 Go 组合共享同一套结构语义（A6 + #311 阶段 4） |
| 自动给节点起名 / 自动推断类型 | 节点 ID 是观测归因键、类型是隐私边界——自动化的漂移比多打几个字贵（A5、A7） |

## 一条纪律：上面这些不能只是口号

- **每条语义都要有用例**；行为类结论要有**变异对照**（把实现退回错写法必须让用例变红），而不是「读码看起来对」；
- **文档里的可复制示例由 CI 扫描**（签名漂了就红），因为 Markdown 代码块不参与编译；
- **破坏性变化**必须写进 release notes，并在冻结面那一节点名。
