# 设计理念

Pulse 的每条设计取舍都有理由。这一页讲**为什么**——好让你在选型、踩边界、或者想「能不能再加个开关」时，知道这个库在守什么。

完整的理念文档（含每条公理的代价与边界）在仓库里：[`docs/design/philosophy.md`](https://github.com/Luo-root/pulse/blob/main/docs/design/philosophy.md)。

## 一句话定位

Pulse 是 Go 的**数据到达驱动**执行引擎，外加一层**图观测**。它只做三件事：

1. **声明**：谁读什么、谁写什么；
2. **推进**：一条 Key 到达（有值或显式跳过）就让等它的节点具备就绪条件——没有边对象、没有「先排序再执行」的调度阶段、没有调度循环；
3. **讲清楚**：跑到哪了、谁在等谁、失败在哪。

它不是**传统的中心调度式 DAG 工作流引擎**——Pulse 同样从 `Requires` / `Provides` 推出依赖图、同样拒绝依赖环、同样给拓扑视图，差别在于推进由 Key 到达驱动而不是中心调度器；重试必须**显式声明**（`Retry` 切面），引擎不做隐式补偿；不是业务框架（不碰 IO、不认识业务字段），不是 DSL（Go 里就是 Go，声明式只在 `pulse/yaml` 那一层存在）。

## 六条你会直接感受到的理念

### 1. 拓扑由数据推出来，不由你写

节点只声明 `Requires` / `Provides`；边是「谁生产这条 Key、谁消费它」推出来的。

**为什么**：写边就会写错边——漏一条、指错一端。而「这条 Key 谁生产」在声明里本来就唯一（一个 Key 至多一个来源，否则报 `ErrDuplicateSource`），既然唯一，边就是**派生视图**。

**你的感受**：不用维护一份会漂的连线表；代价是不支持「同一对节点多条边分别表达」这类图论玩法。

### 2. 声明与到达分开：`pending` 不是到达

槽位只有三态：`pending`（还没到）、`ready`（有值）、`skipped`（显式跳过）。**就绪与跳过都是到达。**

**为什么**：混起来，下游就会在「输入还没来」时以为自己该跳过了；「谁在等谁」也就答不出来——看板会把「还没轮到」与「等名额」画成同一个样子。

**你的感受**：`Get` 阻塞到到达、`TryGet` 非阻塞看一眼、`WaitAll` 报「谁没到」；零值与「没有」是两件事——要区分就写 `skipped`，别拿零值当缺失。

### 3. 跳过是正常语义，不升格为失败；失败也绝不降格成跳过

**为什么**：数据流里「这路没有」是常态（可选输入、分支没走到、上游按条件省略），把它当异常等于逼每个节点写兜底样板；反过来把失败伪装成跳过，会让故障从故障单里消失。

**你的感受**：门闩的判据是「**有没有值**」——一条值都没到才轮到节点自己跳过；意思是**到几个收几个**。想要「缺一条就别跑我」，把 `WaitAll` 的返回值直接 `return`——那是显式的汇聚策略，引擎不替你猜。

### 4. 错误显式，且在最早能判定处报

**为什么**：图跑起来之后的毛病最贵——挂死、超时、静默拿到零值，三种都难查，而且都不指向真正写错的那一行。

**你的感受**：`Start` 直接拒两类静态可判的死图（某条 `Requires` 没人提供、依赖成环——环还会给出**一条具体见证路径**）；`Validate` 让你在装配期反复问；声明式装图（`pulse/yaml`）连子图也会**按引用点逐层**校验；报错文案点名位置（`Sub "b"` 那类），而不是一句「失败」。

### 5. 观测与语义同源，且观测不改语义

**为什么**：两套口径就会漂——看板说 A、日志说 B，谁都对；而观测一旦能改语义，它就不再是观测，是隐式控制流。

**你的感受**：事件与状态**在同一点写**；观察者抛 panic 不会变成节点失败；业务维度只能走 `Attrs`（`Record` 不加具名字段）。代价是：想加一个「引擎认识的业务字段」无处可写，得自己进 `Attrs`。

### 6. 引擎零依赖，能力分层

**为什么**：引擎是别人系统里的地基，不能把依赖树带进宿主的供应链；观测与声明式装图是可选装的能力。

**你的感受**：`pulse` 只用标准库（`go list -deps .` 可以自查），`gopkg.in/yaml.v3` 只被 `pulse/yaml` 使用；依赖箭头单向（`pulse` ← `observe` / `yaml`）。

## 刻意不做

| 不做 | 因为 |
|---|---|
| 中心调度器与「先拓扑排序再执行」 | 数据到达就推进；执行顺序是声明的**结果**，不是前提；拓扑视图是只读出口，不参与推进 |
| 「缺值即跳过」的隐式策略 | 缺失语义必须由节点显式声明（门闩默认到几个收几个，`WaitAll` 才是缺一不可） |
| 回滚外部副作用 | 引擎只管自己的槽位；数据库提交 / HTTP / 写文件那一层要事务、幂等键或补偿，得由你接进来 |
| 隐式补偿与不透明的事务魔法 | 没有单独契约与测试之前不引入——听起来像保证，实际是运气 |
| 把业务维度塞进引擎类型 | `Record` 不加具名字段，`Attrs` 是唯一出口 |
| 在 Go 里造 DSL | Go 里就是 Go；声明式只在 YAML 那一层 |

## 正在变化的一件事：图是定义，执行是实例

Pulse 目前的 `Graph` **同时**是「图的定义」与「一次运行」：`Start` 只能成功一次、`Wait` 结束就释放上下文、槽位与节点状态都挂在图上；`Sub` 还要在运行期才把子图建出来，所以「组合完成但尚未运行时看不到完整结构」「构建 / 绑定错误延迟到运行期」这些限制互相牵连。

目标模型是把它拆开：**`Graph` 是可复用的静态定义（可被多次、并发地执行，也可被多处挂载为子图），`Execution` 承载一次运行的全部状态**。这一步正在按 [#311](https://github.com/Luo-root/pulse/issues/311) 设计并分阶段落地，契约草案与阶段路线见 [`docs/design/object-model.md`](https://github.com/Luo-root/pulse/blob/main/docs/design/object-model.md)。

在那之前，文档里凡是写「`Graph` 是一次运行的世界」的地方，描述的都是**当前实现**；目标形状以对象模型那份文档为准。
