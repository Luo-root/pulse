# 设计理念

Pulse 的每条设计取舍都有理由。这一页讲**为什么**——好让你在选型、踩边界、或者想「能不能再加个开关」时，知道这个库在守什么。

完整的理念文档（含每条公理的代价与边界）在仓库里：[`docs/design/philosophy.md`](https://github.com/Luo-root/pulse/blob/main/docs/design/philosophy.md)。

## 一句话定位

Pulse 的产品方向是**数据驱动、可观测、可组合的 Go workflow-engine 基座**。当前 `pulse` 提供可嵌入的单进程执行内核和图观测；独立的 `pulse-durable` 按节点检查点恢复路线扩展长期运行能力，持久化等待与分布式运行管理仍是后续设计方向，尚未实现。两仓职责与路线见 [开发总纲 #320](https://github.com/Luo-root/pulse/issues/320)。

下面讲的是**执行内核**的三件事；durable 的任务领取、唤醒与接管属于运行管理，两层职责分开：

1. **声明**：谁读什么、谁写什么；
2. **推进**：一条 Key 到达（有值或显式跳过）就让等它的节点具备就绪条件——没有边对象、没有「先排序再执行」的调度阶段、没有调度循环；
3. **讲清楚**：跑到哪了、谁在等谁、失败在哪。

它不是**传统的中心调度式 DAG 工作流引擎**——Pulse 同样从 `Requires` / `Provides` 推出依赖图、同样拒绝依赖环、同样给拓扑视图，差别在于推进由 Key 到达驱动而不是中心调度器；重试必须**显式声明**（`Retry` 切面）——声明之后那一段的槽位写入由引擎按尝试边界管住（失败的那一次不发布给下游），但引擎不做隐式补偿、也不去撤你已经在外部世界里做过的事；不是业务框架（不碰 IO、不认识业务字段），不是 DSL（Go 里就是 Go，声明式只在 `pulse/yaml` 那一层存在）。

## 六条你会直接感受到的理念

### 1. 拓扑由数据推出来，不由你写

节点只声明 `Requires` / `Provides`；边是「谁生产这条 Key、谁消费它」推出来的。

**为什么**：写边就会写错边——漏一条、指错一端。而「这条 Key 谁生产」在声明里本来就唯一（一个 Key 至多一个来源，否则报 `ErrDuplicateSource`），既然唯一，边就是**派生视图**。

**你的感受**：不用维护一份会漂的连线表；代价是不支持「同一对节点多条边分别表达」这类图论玩法。

### 2. 声明与到达分开：`pending` 不是到达

槽位只有三态：`pending`（还没到）、`ready`（有值）、`skipped`（显式跳过）。**就绪与跳过都是到达。**

**为什么**：混起来，下游就会在「输入还没来」时以为自己该跳过了；「谁在等谁」也就答不出来——看板会把「还没轮到」与「等名额」画成同一个样子。

**你的感受**：`Get` 阻塞到到达、`TryGet` 非阻塞看一眼、`WaitAll` 报「谁没到」；零值与「没有」是两件事——要区分就写 `skipped`，别拿零值当缺失。

### 3. 跳过是正常语义，不升格为失败；失败也绝不降格成跳过

**为什么**：数据流里「这路没有」是常态（可选输入、分支没走到、上游按条件省略），把它当异常等于逼每个节点写兜底样板；反过来把失败伪装成跳过，会让故障从故障单里消失。

**你的感受**：门闩的判据是「**有没有值**」——一条值都没到才轮到节点自己跳过；意思是**到几个收几个**。想要「缺一条就别跑我」，把 `WaitAll` 的返回值直接 `return`——那是显式的汇聚策略，引擎不替你猜。

### 4. 错误显式，且在最早能判定处报

**为什么**：图跑起来之后的毛病最贵——挂死、超时、静默拿到零值，三种都难查，而且都不指向真正写错的那一行。

**你的感受**：启动那一刻（`Run` / `NewExecution` / `Start()` 同一套判据）直接拒两类静态可判的死图（某条 `Requires` 没人提供、依赖成环——环还会给出**一条具体见证路径**）；`Validate` 让你在装配期反复问；声明式装图（`pulse/yaml`）连子图也在 `Load` 那一刻按引用点校验、并点明**挂载路径**；报错文案点名位置（`Sub "b"` 那类），而不是一句「失败」。

### 5. 观测与语义同源，且观测不改语义

**为什么**：两套口径就会漂——看板说 A、日志说 B，谁都对；而观测一旦能改语义，它就不再是观测，是隐式控制流。

**你的感受**：事件与状态**在同一点写**；观察者抛 panic 不会变成节点失败；业务维度只能走 `Attrs`（`Record` 不加具名字段）。代价是：想加一个「引擎认识的业务字段」无处可写，得自己进 `Attrs`。

### 6. 引擎零依赖，能力分层

**为什么**：引擎是别人系统里的地基，不能把依赖树带进宿主的供应链；观测与声明式装图是可选装的能力。

**你的感受**：`pulse` 只用标准库（`go list -deps .` 可以自查），`gopkg.in/yaml.v3` 只被 `pulse/yaml` 使用；依赖箭头单向（`pulse` ← `observe` / `yaml`）。

## 刻意不做

下列边界针对执行内核。durable 后续的检查点、等待、任务领取与接管属于运行管理；核心没有中心调度循环，不妨碍那一层有自己的持久调度协议。

| 不做 | 因为 |
|---|---|
| 中心调度器与「先拓扑排序再执行」 | 数据到达就推进；执行顺序是声明的**结果**，不是前提；拓扑视图是只读出口，不参与推进 |
| 「缺值即跳过」的隐式策略 | 缺失语义必须由节点显式声明（门闩默认到几个收几个，`WaitAll` 才是缺一不可） |
| 回滚外部副作用 | 引擎只管自己的槽位；数据库提交 / HTTP / 写文件那一层要事务、幂等键或补偿，得由你接进来 |
| 隐式补偿与不透明的事务魔法 | 没有单独契约与测试之前不引入——听起来像保证，实际是运气 |
| 把业务维度塞进引擎类型 | `Record` 不加具名字段，`Attrs` 是唯一出口 |
| 在 Go 里造 DSL | Go 里就是 Go；声明式只在 YAML 那一层 |

## 已经落地：图是定义，执行是实例

把「图的定义」与「一次运行」拆开的两半都已经落地。**组合与静态校验**：静态组合 `Sub` 在装配期就把子图建好，装配完不运行即可沿静态挂载边递归看全整棵树（`Topology()`），子图的静态毛病（无来源 / 出口没人产出 / 依赖环）在装图那一刻按引用点报出来、报文点明**挂载路径**；端口（`DeclareInput` / `DeclareOutput`）是唯一的接线面，`Validate()` 递归判一遍、**通过即封口**（定义连同挂着的子图整棵从此不再变化）。

**执行**：`Graph` 是**可复用的静态定义**，一次运行的 ctx / 输入值 / 槽位 / 节点状态 / 首错 / 取消域全在新的 `Execution` 里——同一张图可以顺序跑很多次、并发跑很多次，也可以挂在多处当子图（每个挂载位置一份自己的子执行），一次运行的取消 / 失败 / 完成不污染定义，也不污染别的运行。输入（`Inputs` + `Seed` / `SkipSeed`）属于**这一次运行**，定义只声明「这条键从外面来」（`DeclareInput`）。

阶段 4（快照 / 观测 / YAML 对齐）已实现（#319，主干合入与发布状态以 PR / release 为准）：Topology 看完整静态接口，Execution 快照看本轮进度，Mermaid 可叠状态，YAML Analyze 无需注册表。阶段 5（迁移与发布）继续按 [#311](https://github.com/Luo-root/pulse/issues/311) 收口；**阶段 1（静态组合）/ 2（`Execution` 拆分）/ 3（事务性 `Retry`）都已落地**，契约与逐阶段落地情况见 [`docs/design/object-model.md`](https://github.com/Luo-root/pulse/blob/main/docs/design/object-model.md)。
